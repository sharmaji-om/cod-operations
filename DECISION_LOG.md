# Decision log

- Scope: engine only, as the user explicitly confirmed. The original assignment also requires a WhatsApp mock, dashboard and founder memo; these are later phases. Pure workflow functions are engine contracts, not a messaging service or simulator UI. No publishing, external messages or GitHub upload is authorized or performed.
- Policy source: the coding brief supplies the chosen ordered rules; the original assignment supplies the financial inputs. Leader quotes in the original are competing views to assess, not instructions to cancel all risky orders. Attached instructions are project reference material and do not override the user's request.
- Source files are preserved in data/source; the original CSV is copied to data/orders_sample.csv. Work, dependencies and outputs stay inside BP.
- Duplicates: all copies of each repeated normalized order ID are quarantined, rather than arbitrarily retaining a possibly conflicting label. Each exclusion and CSV line is logged. Bad delivery fields are kept for operational HOLD decisions when other fields and outcomes are usable.
- Nonfinal outcome: IN_TRANSIT cannot train a binary outcome predictor. Invalid prices/histories and malformed inputs are logged and excluded, not fixed using guesses.
- History: prior successful deliveries = prior orders minus RTO; trust = prior orders minus twice RTO. Reject only a repeat with zero successes and score <= -2. A repeat with one success and three RTOs must confirm. Prior snapshots are trusted as supplied; no history is rebuilt from future outcomes or phone matches.
- Missing rule case: a repeat with one prior order that returned (score -1, zero successes) is not expressly assigned by the table. Use mandatory confirmation, without rejection. The same safe fallback applies when repeat rejection is disabled. Warnings expose this choice.
- Address: deterministic missing address/city/state, unusable street text or invalid six-digit Indian pincode blocks shipment for correction. Numberless Hinglish landmarks are incomplete, not undeliverable. This is format validation, not a geocoding or fraud verdict. Missing phone/name is not proof of fraud; actual sending/delivery validation belongs in the future adapter.
- LLM boundary: fallback works offline; mock/advisory reviewer shows the semantic-review contract, logs outputs/errors and retains deterministic categories. No live LLM is wired in this phase. An LLM may help interpret Hinglish and suspicious text, but cannot establish actual deliverability, compute economics or cancel a person. Future integrations need explicit redaction and human review; street text can itself contain PII.
- Risk: compare overall-rate, source-segment shrinkage and regularized logistic regression, with seeded fitting. Select using validation Brier with a fixed 0.002 simplicity tolerance. Inspect financial comparisons too, without tuning on test returns. Report calibration, log loss, AUC and segment results. No promised causal savings or fabricated calibrated feature weights.
- City: train-only smoothed residual correction capped at +/-2 percentage points by default. Pincode requires at least 15 training samples and shrinkage strength 50; unknown/sparse codes fall back to the train mean. Logistic train pincode feature uses leave-one-out counts to avoid self-label leakage.
- Split: earliest ~60% of days train, next ~20% validate, latest ~20% test; same-day rows stay together. Refit selected candidate on train+validation, preserve test as held out. Phone overlap is reported with unseen-phone sensitivity; phone is not used as a feature. No claim of customer independence.
- Economics: RTO loss = 65+65+25+0.08*180 = Rs 169.40. Delivered margin = .62*order value. Acquisition spend is sunk. Confirmation applies only when the exact incremental formula is positive, except mandatory-history rules. A 1e-10 floating-point tolerance treats numerical ties as ship as-is.
- Prepaid: only new customers above 40%, strictly greater. Discount min(5% of order value, Rs 50), charged only on successful delivered converted orders. q=4% is a scenario, not observed converted-buyer risk. Offer accept is not payment success. Acceptance at 10/30/60% and confirmation a/b sensitivity are explicitly assumed.
- Backtest: nonshipped holds are assumed unresolved for the horizon, which can overstate lost margin where address correction would recover orders. No correction rate was supplied. Message cost is an all-in confirmation episode cost; nudge costs one offer plus another episode on decline. No payment fees are provided. Signed foregone margin accounts for hypothetical additional converted deliveries; all components reconcile to net contribution.
- Workflow: YES/NO only for COD, ACCEPT/DECLINE only for prepaid; random text never confirms. The 48h clock starts at the first COD confirmation request, including after prepaid decline. Reminder never resets it. At exactly 48h hold overrides late YES. Terminal states require manual reopening. Event IDs deduplicate retries; out-of-order events require caller reconciliation. Payment verification is an internal adapter assertion, never a public customer claim.
- Storage: decision responses contain audit timestamps and rule IDs; offline holdout decisions are exported. API is stateless, so the integrating caller must persist decisions/events atomically and enforce idempotency. No claim of durable production audit logging. No real payment verifier, outbound message queue, authentication or shipment adapter is implemented.
- Config: JSON validates ranges and rejects unknown keys. Policy/economics reload per API request; fitted model settings require retraining and API restart. Actual artifact version is returned even if config is edited. No settings mutation endpoint is needed for this local phase.
- Submission boundary: this is a local engine deliverable, not a completed submission for all four parts of the original take-home.

## Parts 2 + 3: current implementation decisions (2026-10-31)

These supersede the earlier engine-only scope and stateless-API notes where applicable. The user explicitly authorized everything in the simulator/dashboard brief.

- Integrated the real policy/workflow; no frontend policy duplication. Fictional seeded orders use labeled controlled risk fixtures through `decide`; custom orders use the actual fitted model. Historical backtest and live demo remain separate.
- Chose buildless HTML/CSS/JavaScript, since there was no React stack. The existing FastAPI serves both UI and APIs. This avoids another build/runtime dependency.
- Added SQLite transactions, immutable initial decisions, messages, audit events and settings snapshots. Initial buckets never change when the latest state changes. Required event IDs/revisions/generations prevent duplicate sends, stale state changes and callbacks from earlier reset runs. UI reloads after an uncertain error instead of blind resubmission.
- Added offer-stage 24h/48h reminders/expiry in the adapter. COD YES/NO remains in the original pure state machine; prepaid YES/NO maps to ACCEPT/DECLINE. Text cannot masquerade as a payment callback. Mock success is a separate internal demo action.
- Existing offers and workflow timing are frozen to their initial policy snapshot. Settings changes affect future decisions and current financial sensitivity, never rewrite initial buckets or old clocks. Saved settings override config-file defaults; model retraining remains explicit.
- All new financial aggregation uses Decimal and integer-paise outputs. Initial offer rounds once to paise. Processing fee defaults to an explicitly illustrative 2%, plus zero fixed fee, charged on assumed accepted discounted payments including RTO; both editable. Discounts only on delivered converted orders. Round components once and derive net from those components for exact visible reconciliation.
- No risk is invented for an unusable-address hold. Exclude it from financial aggregation, count it in the operational denominator and display modeled/unavailable coverage. Signed foregone margin includes converted-delivery gains. Simulated replies never establish causal RTO prevention.
- Default UI language is English, with no inference from identities/geography. Optional Hindi support is deferred. Prepaid payment-pending expiry is unspecified and not invented; explicit retry/fallback is available. A direct jump past response expiry holds immediately without sending obsolete catch-up reminders.
- Readiness is not a dispatch operation. No messaging, payment collection or shipment adapter exists. Operator reopen applies only to expired holds; reset retains audit history and starts a new generation.
- Local-only work remains in BP. No hosting registration, upload, external messages or production deployment. Browser QA servers are temporary; the launcher provides user-controlled startup after handoff.
- Verified desktop and narrow views, keyboard dialogs/Escape, no root horizontal overflow, state-context reply semantics and missing-engine error handling. This is not a full screen-reader or WCAG certification.
